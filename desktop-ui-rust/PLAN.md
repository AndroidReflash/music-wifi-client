# План десктопного приложения musicwifi на Rust

## Назначение файла

Этот файл — рабочая память проекта. Новая сессия должна читать его вместо истории чата и после каждого подшага обновлять статус. 
План не заменяет чтение кода: перед изменением конкретного модуля всё равно открываются только те файлы, которые нужны для этого шага.

Текущий статус: каркас пакета создан, пользователь проверил, что он собирается и открывает окно. 
Доступ к плееру, настройкам, сети и горячим клавишам ещё не подключён. Код по этому плану пока не писался дальше каркаса.

## 1. Что уже решено

### 1.1. UI на iced

Десктопный интерфейс пишется на `iced` версии 0.13.1. Версия выбрана потому, что её исходники уже есть в локальном cargo-реестре, 
и API можно проверять по фактическому коду, а не угадывать.

`iced` — retained-библиотека: она хранит дерево виджетов и состояние элементов интерфейса. 
Это не то же самое, что immediate-mode `egui`, который хранит только память по идентификаторам.
Памяти `iced` расходует больше, зато даёт явное разделение «сообщение → обновление состояния → отрисовка»
и встроенные подписки на внешние события. По скорости выполнения преимущества над `egui` нет;
выбор сделан ради архитектуры, а не ради CPU.

### 1.2. Один бинарник, JVM-версия остаётся

Новый пакет называется `desktop-ui-rust`, исполняемый файл — `musicwifi-rust`. Ядро `player_core` подключается как path-зависимость:

```text
player_core = { path = "../composeApp/src/main/rust" }
```

На десктопе `player_core` собирается как `rlib` — обычная Rust-библиотека, которая линкуется в исполняемый файл. 
На Android то же ядро продолжает собираться как `cdylib` — динамическая библиотека для `jniLibs`, к которой 
обращаются через `uniffi`. Поэтому на десктопе не нужны ни `.so`, ни `.jar`, ни JVM.

JVM-версия не удаляется и не переписывается. Обе версии сосуществуют; Rust-версия нужна как замена для десктопа, 
а не как замена Android или текущего Compose-приложения.

Общий Cargo-workspace не создаётся. Причина практическая: `./rust-test.sh` содержит `cargo test --workspace`, а `./rust.sh` 
использует `cargo ndk`. Если добавить десктопный пакет в workspace, Android-скрипты начнут собирать лишнее
или поведут себя иначе. Новый пакет живёт отдельно и собирается своим `cargo`.

### 1.3. Настройки портативные, без миграции

Настройки нового приложения лежат рядом с исполняемым файлом:

```text
<каталог бинарника>/database/settings.json
```

При запуске через `cargo run` это будет `desktop-ui-rust/target/debug/database/settings.json`,
у релизного бинарника — рядом с `musicwifi-rust`. Старый DataStore-файл JVM-версии (`settings.preferences_pb`) 
не читается и не преобразуется. Первый запуск начинает со значений по умолчанию. 
Это осознанное решение: миграция protobuf в JSON не нужна, а старые настройки остаются у старого приложения.

Запись атомарная: сначала временный файл в том же каталоге, затем переименование.
Битый файл не затирается молча: приложение сообщает об ошибке, работает на значениях по умолчанию и оставляет файл для ручного исправления.

### 1.4. Первый рубеж и второй рубеж

Первый рубеж:

- локальные файлы;
- главный экран, список, плеер, обложка, пластинка, спектр;
- все диалоги: IP/тема/видимость, звук, эквалайзер, горячие клавиши, автоплей;
- выбор папки своим оверлеем;
- оконные горячие клавиши;
- глобальные горячие клавиши X11.

Сеть, SSE, онлайн-плейлист и реальное подключение по IP — второй рубеж.
Диалог IP в первом рубеже сохраняет адрес и переключатель, но не подключается.
Онлайн-режим показывает честное состояние «сервер не подключён», а не пустой успешный список.

Автоплей по последовательности остаётся на втором рубеже. Чтобы переключатель в диалоге не врал, 
в первом рубеже он будет неактивен с пояснением, что поведение появится позже. Это лучше, чем тумблер, 
который сохраняет значение, но ничего не делает.

### 1.5. Linux/X11, без обещаний про Wayland

Первая версия ориентируется на Linux и X11. Оконные горячие клавиши работают через события окна.
Глобальные горячие клавиши работают через X11 `GrabKey`. Если обнаружен Wayland, приложение честно сообщает,
что глобальные клавиши недоступны; оконные клавиши при этом продолжают работать.

### 1.6. Выбор папки без нативного диалога

Нативный диалог не используется. Повторяется текущий диалог Compose: оверлей, текущий каталог, переход вверх, список подпапок, 
«Применить» и «Отмена». Причина — визуальное соответствие и одинаковое поведение на разных Linux-окружениях.

### 1.7. Горячие клавиши — собственный формат

AWT-коды (`KeyEvent.VK_*`) не переносятся в настройки. Вводится собственный enum `HotkeyCode` для 
поддерживаемого набора клавиш и отдельные таблицы перевода:

- в `iced::keyboard::Key` для оконных клавиш;
- в X11 keysym для глобальных клавиш.

Старые числовые значения не мигрируются. Это позволяет не тащить числовые константы AWT в Rust и явно видеть поддерживаемый набор.

### 1.8. Сборка

Пользователь собирает и запускает вручную. Агент не запускает сборку и не считает код проверенным, пока пользователь не подтвердил.

Для десктопного пакета:

```bash
cd /home/void/StudioProjects/musicwifi/desktop-ui-rust
cargo build --release
./target/release/musicwifi-rust
```

Это не противоречит правилу `./rust.sh` для Android: `./rust.sh` собирает Android-ядро, две ABI и Kotlin-биндинги.
Десктопный пакет в этот процесс не входит. Если позже понадобится единая команда, можно добавить отдельный скрипт, но сейчас этого не делаем.

## 2. Архитектура нового приложения

### 2.1. Слои

Код делится по роли, а не по экранам:

- `src/main.rs` — только объявления модулей и запуск приложения. Никакой логики экрана и плеера.
- `src/app/` — состояние приложения, сообщения iced, `update`, запуск фоновых задач, подписки. 
   Здесь же композиция того, что в JVM-версии собирал DI.
- `src/settings/` — модель настроек, значения по умолчанию, чтение и запись JSON, формат горячих клавиш.
- `src/repository/` — песни, офлайн-наблюдение, сеть. Сюда уходит логика Kotlin-репозиториев.
- `src/platform/` — окно, горячие клавиши, X11, выбор папки.
- `src/ui/` — только отрисовка: главный экран, элементы, диалоги, кастомные виджеты. Логики здесь нет; UI читает состояние и отправляет сообщения.
- `src/ui/assets/` — изображения и шрифты интерфейса, которые встраиваются в бинарник через `include_bytes!`.
- `src/ui/icons/` — по отдельному файлу на каждую иконку; иконки рисуются через `canvas`, если их нельзя использовать как SVG/XML.

Правила модулей из `readme-rust-mobile.md` сохраняются: каталог с `mod.rs`, в `mod.rs`
только объявления модулей и `pub use`, логика в отдельных файлах, тип, его `impl` и тесты — вместе. 
Корневых `.rs` рядом с каталогами нет, кроме `main.rs` и общего `testkit.rs`.

### 2.2. Потоки и сообщения

UI-поток iced не должен блокироваться. Блокирующие операции ядра уходят в отдельные потоки:

- `Player::new` открывает звуковое устройство;
- `FolderWatcher::new` синхронно сканирует папку и сразу вызывает колбэк;
- `QuicSession::connect` ждёт установления соединения;
- `QuicSession::send_command` использует `block_on`;
- `Player::output_devices` перечисляет устройства;
- `Player::track_cover` читает файл обложки.

Схема:

1. Поток или колбэк ядра отправляет событие в канал.
2. iced `Subscription` забирает событие из канала и превращает его в `Message`.
3. `update` меняет состояние приложения.
4. `view` перерисовывает интерфейс.

Долгие операции, у которых нет потока событий, запускаются отдельным `std::thread`; результат приходит сообщением.
Это проще, чем заводить второй tokio-рантайм в UI: ядро уже владеет своими рантаймами, а вложенный `block_on` в чужом рантайме может паниковать.

Быстрые команды плеера (`play`, `pause`, `seek`, `set_volume`, `set_equalizer`) можно вызывать прямо из `update`: 
они только кладут команду в очередь плеера и не ждут её выполнения.

### 2.4. Состояние приложения

`App` хранит:

- текущие настройки;
- состояние экрана: локальный/онлайн список, выбранная дорожка, прокрутка;
- состояние плеера: `Idle`/`Playing`/`Paused`, позиция, длительность, громкость, эквалайзер;
- последние полосы спектра;
- текущую обложку;
- открытый диалог и состояние захвата горячей клавиши;
- статус сети и ошибку сети;
- состояние глобальных клавиш X11.

`Message` делится на группы: запуск, события плеера, тики позиции, тики спектра, изменения плейлиста, действия пользователя,
диалоги, горячие клавиши, сеть, закрытие окна.

`update` не выполняет блокирующих вызовов. Если нужно сделать что-то долгое, он запускает поток и возвращает `Task::none()`; 
результат придёт сообщением. Тики позиции и спектра приходят через `Subscription`.

### 2.5. Завершение работы

По закрытию окна приложение должно:

1. снять глобальные горячие клавиши X11;
2. остановить SSE-подписку, если она есть;
3. остановить `FolderWatcher`;
4. вызвать `Player::shutdown`;
5. закрыть окно.

Для этого запрос на закрытие обрабатывается вручную; окно не закрывается мгновенно, пока фоновые ресурсы не отпущены.
Если что-то не удалось остановить, это сообщается, а не скрывается.

## 3. Первый рубеж

После каждого подшага: тесты, короткий отчёт, остановка. Пользователь собирает и проверяет запуск.

### 3.1. Каркас и зависимости

Статус: выполнено частично. Созданы `desktop-ui-rust/Cargo.toml` и временный `src/main.rs`. 
Пользователь подтвердил, что окно собирается и открывается.

Что сделать дальше:

- перенести `State`, `Message`, `update` и `view` из `main.rs` в `app/` и `ui/`;
- оставить в `main.rs` только `mod` и запуск;
- добавить зависимости по мере необходимости: `serde`, `serde_json`, `x11rb`;
- не добавлять зависимости, которые ещё не используются.

Критерий: `main.rs` не содержит логики экрана, а приложение по-прежнему открывает окно 900×600 с заголовком `musicwifi`.

### 3.2. Настройки и `HotkeyCode`

Создать модель `Settings` со всеми ключами, которые сейчас есть в `SettingsRepositoryImpl`:
адрес сервера, онлайн/офлайн, папка, цвет темы, видимость визуализатора/пластинки/картинки,
устройство вывода, громкость, эквалайзер, кольцо/малый размер, глобальные клавиши, 
shuffle/repeat, автоплей, назначения клавиш. Значения по умолчанию повторяют Kotlin-версию.

Реализовать:

- загрузку JSON;
- атомарную запись;
- поведение при отсутствующем и битом файле;
- формат цвета темы;
- `HotkeyCode` и `HotkeyBinding`;
- перевод в `iced::Key` и в X11 keysym.

Почему отдельно: настройки нужны и UI, и платформе, и сети. Если формат клавиш сделать внутри UI, его потом придётся выковыривать.
Тесты: значения по умолчанию, round-trip JSON, битый файл, атомарная запись, разбор и печать комбинаций, перевод известных клавиш.
Критерий: настройки переживают перезапуск, файл лежит рядом с бинарником, старый protobuf не читается.

### 3.3. Ядро приложения и плеер

Создать `PlayerHandle` или эквивалент:

- создание `Player` в фоне;
- сообщение «плеер готов» или «плеер не открылся»;
- канал событий плеера;
- периодический снимок состояния;
- канал спектра;
- создание `FolderWatcher` в фоне;
- загрузка локального плейлиста;
- обработка ошибок устройства вывода.

Почему в фоне: `Player::new` и `FolderWatcher::new` блокирующие. Если вызвать их в `update`, 
окно замрёт на время открытия устройства и сканирования папки.

Критерий: папка сканируется, дорожка играет, пауза/переход/перемотка работают, ошибка устройства показана в интерфейсе.

### 3.4. Оболочка UI

Сделать:

- стартовый и минимальный размер 900×600, заголовок `musicwifi`;
- чёрный фон, белый текст, цвет интерфейса из настроек; временную `iced::Theme::Dark` в скелете надо заменить своим чёрным стилем;
- встроенный шрифт;
- встроенные иконки;
- стиль полосы прокрутки;
- базовую сетку главного экрана.

Шрифт встраивается потому, что системный шрифт в iced и Compose может различаться, а от этого зависят размеры текста и вся сетка.
Если после сравнения метрики расходятся, подбирается другой встроенный шрифт, а не подгоняется каждый экран отдельно.

Иконки из Compose-ресурсов не конвертируются в PNG по умолчанию. Android VectorDrawable в XML — не SVG,
и iced его не читает, поэтому каждая иконка рисуется отдельным файлом через `canvas` в `src/ui/icons/`.
Изображения и шрифты, которые действительно нужны как файлы, лежат в `src/ui/assets/`.
Если для конкретной иконки canvas окажется неподходящим, только тогда рассматривается растровый вариант, и он кладётся в `assets`.

Критерий: пустое окно визуально совпадает с JVM-версией по цветам и сетке.

### 3.5. Главный экран

Портировать desktop-раскладку:

- верхняя полоса;
- список слева с прокруткой;
- справа квадрат с обложкой, пластинкой или спектром;
- название с бегущей строкой;
- кнопки управления;
- ползунок перемотки;
- индикатор позиции и длительности.

Детали:

- обложка читается и декодируется вне UI-потока; при ошибке картинка просто отсутствует;
- спектр: колбэк складывает последние полосы в `Arc<Mutex<Vec<f64>>>`, UI читает их с частотой кадров; при `Idle` 
  список пуст, на паузе картинка замирает;
- ползунок перемотки во время удержания показывает локальное положение, `seek` отправляется на отпускании;
- список сначала рисуется через `scrollable` и `Column`; на большой папке проверяется плавность. 
  Если кадры просаживаются, рисуется только видимый диапазон. Это не «костыль», а измеренное решение по производительности.

Критерий: локальный плейлист, играющая дорожка, перемотка, спектр, обложка, прокрутка.

### 3.6. Диалоги

Портировать:

- `ChangeIpDialog`: адрес, онлайн/офлайн, цвет темы, видимость визуализатора/пластинки/картинки, 
  кольцо/малый размер, звук, горячие клавиши, автоплей;
- `EqualizerDialog`: полосы, предел дБ, сброс;
- выбор папки: свой оверлей;
- диалог горячих клавиш: захват комбинации, удаление, глобальный режим, статус X11.

Панельные настройки (разделитель и прозрачная панель) на десктопе в текущей JVM-версии пустые, поэтому в Rust-версии их тоже нет.

Диалоги — модальные оверлеи, а не отдельные окна. Причина: меньше проблем с фокусом, глобальными клавишами и позиционированием; 
Compose-диалоги тоже модальные.

Критерий: все диалоги открываются, настройки переживают перезапуск, эквалайзер и устройство вывода действуют сразу, 
выбор папки работает без нативного диалога.

### 3.7. Горячие клавиши

Оконные:

- подписка на клавиатуру iced;
- сопоставление с `HotkeyBinding`;
- подавление при фокусе в поле поиска;
- учёт автоповтора через набор зажатых клавиш;
- сброс состояния при потере фокуса окна.

Глобальные X11:

- отдельный поток на `x11rb`;
- `GrabKey` на корневом окне;
- маски Shift/Ctrl/Alt;
- варианты с Caps Lock и Num Lock;
- ответы «захвачено», «отклонено», «недоступно»;
- повтор для перемотки и громкости с задержкой и шагом;
- снятие захватов при выходе и при выключении глобального режима.

Действия те же, что в Kotlin: shuffle, previous, play/pause, next, repeat, ±5 секунд, ±5% громкости.

Критерий: назначение, снятие, работа в окне и вне окна, повтор при удержании. При одновременно запущенной JVM-версии глобальные клавиши конфликтуют; проверять по одной.

## 4. Второй рубеж: сеть, SSE, автоплей

### 4.1. Новые API ядра

Добавить отменяемую SSE-подписку. Причина: текущий `subscribe_sse` блокирующий и бесконечный; `subJob.cancel()`
в Kotlin не прерывает native-вызов, поэтому поток и сессия остаются жить.

Предлагаемая форма:

- объект-токен с `cancel()` и `is_cancelled()`;
- токен будит заблокированное чтение, а не просто выставляет флаг;
- метод подписки принимает токен и завершает цикл при отмене;
- старый экспорт остаётся, чтобы Android не сломался мгновенно.

Добавить вариант `send_command`, возвращающий `Result<Vec<u8>, Error>`. 
Причина: сейчас пустой ответ и сетевая ошибка неразличимы; пустой плейлист — нормальный успех, а ошибка должна попадать в `fetchError`.
Старый метод можно оставить для совместимости, но новые вызовы должны использовать вариант с `Result`.

### 4.2. Android

Обновить `NetworkRepositoryImplRust.observeServerUpdates()`:

- создать токен на каждый адрес;
- передать его в отменяемую подписку;
- при смене адреса и в `awaitClose` вызвать `cancel()`;
- отменить корутину после отмены токена.

Обновить `fetchPlaylist`:

- использовать вариант с `Result`;
- при ошибке писать текст в `_fetchError`;
- пустой успешный список не считать ошибкой.

Проверка: `./rust.sh` перегенерирует Kotlin-биндинги; `./rust-test.sh` проходит; 
Android собирается; смена адреса не оставляет старых SSE-циклов; ошибка сети видна в интерфейсе.

### 4.3. Десктопная сеть

Портировать:

- кэш `QuicSession` по адресу;
- подключение;
- получение плейлиста;
- SSE-подписку;
- переподключение;
- статус сервера.

Каждая сессия получает поколение. Сообщения от старого поколения игнорируются,
чтобы после смены адреса старый поток не перезаписал новый плейлист. Это не обходной путь, а явная защита от гонки.

Все блокирующие вызовы — в отдельных потоках. Отмена — по токену при смене адреса и выходе.

Проверка: список приходит с сервера, обновляется по SSE, смена адреса не течёт.

### 4.4. Автоплей

Повторить поведение Kotlin:

- при первом непустом списке запустить случайную дорожку;
- снять ожидание при любом действии пользователя;
- не запускать повторно после ручной остановки.

Проверка: включённый автоплей стартует один раз, выключенный ничего не делает.

### 4.5. Готовность второго рубежа

- Локальные и сетевые дорожки.
- SSE и переподключение.
- Автоплей.
- Все настройки.
- Android собирается и больше не течёт на SSE.

## 5. Known defects and constraints

Это не список «приемлемых мелочей», а известные дефекты и ограничения, которые нельзя терять.

1. Отмена SSE в Android не останавливает native-цикл. Причина: `subJob.cancel()` отменяет корутину, но `subscribe_sse` продолжает блокирующее чтение. Исправляется новым токеном во втором рубеже.
2. `send_command` возвращает пустой массив и при ошибке. Нельзя отличить пустой плейлист от сетевого отказа. Исправляется вариантом с `Result`.
3. `getServerConfig` сейчас no-op. Не строить на нём логику и не выдавать его за работающий конфиг.
4. `FolderWatcher::new` синхронно сканирует папку и вызывает колбэк. Его нельзя создавать в UI-потоке.
5. `Player::new` блокирующий. Его нельзя создавать в UI-потоке.
6. `QuicSession::send_command` использует `block_on`. Его нельзя вызывать из чужого tokio-рантайма.
7. `subscribe_sse` блокирующий. Его нельзя вызывать из UI-потока.
8. В `AppModuleJvm.kt` есть комментарий про `jpackage.app-path`, который к текущей задаче не относится. Не трогать.

## 6. Риски

- Список в iced не виртуализирован по умолчанию. На большой папке возможны просадки; проверяется на нескольких тысячах файлов.
- Метрики шрифта в iced и Compose различаются. Для близкой копии понадобится встроенный шрифт.
- Порт X11 на `x11rb` — самый объёмный кусок платформенного слоя: маски, XKB, Num Lock, Caps Lock, ошибки захвата.
- Глобальные клавиши двух запущенных версий конфликтуют.
- iced не даёт готовых модальных диалогов; все настройки и выбор папки — оверлеи.
- Сетевые ошибки и отмена SSE требуют аккуратной работы с поколениями и токенами, иначе старые сообщения будут перезаписывать новое состояние.
- Автоплей в первом рубеже выключен; это видимое ограничение, а не скрытая заглушка.
